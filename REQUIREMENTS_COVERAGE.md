# Requirements Coverage

This document maps the insurance SOP harness requirements to the current implementation of SOP-Guided-Conversational-Agent-Meiqi.

## 1. Fixed workflow with natural conversation

**Requirement:** The agent must follow four fixed phases while still conversing naturally.

**Implementation:** LangGraph routes every turn through:

```text
VERIFY_ID → RESOLVE_INTENT → PROCESS_CASE → POST_PROCESS → COMPLETE
```

Python controls phase transitions and safety gates. OpenAI interprets natural language and generates the final response from authorized facts.

Relevant modules: `app/workflow.py`, `app/stages/`, and `app/interpreter.py`.

## 2. VERIFY_ID controls

**Requirement:** Do not disclose claim details or advance before identity verification. Require at least three matching PII fields from full name, DOB, phone, email, or SSN last four digits.

**Implementation:** The identity stage validates evidence against the fixture repository and keeps claim data unavailable until verification succeeds. It supports partial answers, clarification, field refusal, alternate identity fields, incorrect values, and repeated verification failures.

Case hints stated during verification, such as a denied healthcare claim from January, are stored without disclosing protected claim data and reused after verification.

Relevant modules: `app/stages/verify_identity.py`, `app/identity_guard.py`, `app/repository.py`, and `app/models.py`.

## 3. RESOLVE_INTENT and PROCESS_CASE flexibility

**Requirement:** Allow flexible interpretation of messy language and ambiguity while keeping answers grounded.

**Implementation:** OpenAI Structured NLU extracts intent, requested fields, case hints, emotion, identity evidence, and workflow actions. Python validates the result, selects only authorized claims, retrieves facts, and enforces the allowed workflow path.

The final response is generated by OpenAI using the customer message, conversation context, deterministic draft, and authorized facts. Python guards the generated response before delivery.

```text
Customer message
  → OpenAI Structured NLU
  → Python authorization and fact retrieval
  → OpenAI final response generation
  → Python factual and privacy guards
  → Customer response
```

Relevant modules: `app/interpreter.py`, `app/response_service.py`, `app/guards_runtime.py`, and `app/factual_guard.py`.

## 4. POST_PROCESS email summary

**Requirement:** Offer an email summary containing the discussion, claim outcome, and follow-up items. Require an explicit send or skip decision.

**Implementation:** The post-process stage requires explicit consent, supports send/skip/revoke behavior, builds a deterministic summary, and writes approved email content to the demo outbox.

The current implementation does not claim external delivery. SMTP or a production email provider can be added behind the existing outbox boundary.

## 5. Scope control and human escalation

**Requirement:** Reject out-of-scope questions politely and offer a human representative after repeated irrelevant attempts.

**Implementation:** Out-of-scope questions are classified by OpenAI, rejected without claim disclosure, and counted in session state. Repeated out-of-scope turns trigger a human-transfer offer. Explicit human requests can be routed at supported phases.

Relevant modules: `app/interpreter.py`, `app/stages/process_case.py`, `app/escalation.py`, and `app/handoff.py`.

## 6. Cross-phase memory

**Requirement:** Remember useful information when it is stated, even if it belongs to a later phase.

**Implementation:** Session state stores identity evidence, case hints, intent, requested fields, answered fields, pending fields, and conversation history. SQLite checkpoints preserve this state across API requests.

## 7. Emotional support and SOP recovery

**Requirement:** Recognize frustration, anxiety, anger, confusion, and refusal; respond with empathy; explain required SOP steps; offer alternatives; and escalate when persuasion should stop.

**Implementation:** OpenAI NLU extracts emotion independently from business intent. The workflow preserves the business request, adds empathy when appropriate, explains why identity verification or consent is required, offers alternative identity fields, tracks repeated resistance, and offers human support when escalation thresholds are reached.

The agent does not bypass identity or consent gates in response to emotional pressure.

## 8. Demo and delivery requirements

| Requirement | Current status |
|---|---|
| Hosted demo URL | Not configured; requires deployment to a public host |
| Docker image / repository | Dockerfile and Docker Compose are included |
| API auth token for AI model | `OPENAI_API_KEY` is accepted through environment configuration |
| Simple test UI | Included at `/` and served by FastAPI |
| Full workflow demo | Supported through the UI and API session flow |
| End-to-end API regression | 15 API-only cases with a live progress bar |

## 9. Verification flow

```bash
export OPENAI_API_KEY="your API key"
export NLU_MODE=openai
docker compose up --build -d
```

Then open <http://localhost:8000> and exercise identity verification, remembered case hints, claim processing, emotional recovery, out-of-scope handling, human escalation, and email send/skip consent.

Run the API-only regression set:

```bash
python sop_agent_update/tools/run_api_regression_15.py
```

## 10. Current demo limitations

- Email delivery is a demo outbox, not a production SMTP/provider integration.
- Human handoff creates a demo ticket unless an external ticketing system is integrated.
- SQLite is appropriate for a single-instance demo; production replicas should use a shared database and distributed locking.
- A hosted URL still needs to be provisioned by deploying the Docker Compose service to a reachable host.
